# CS-255_SNHU -- System Analysis & Design

# DriverPass System

## Project Summary

This project focused on designing a web-based system for DriverPass, a company that offers driver education services. The goal was to create a platform where students could schedule lessons online, take practice tests, and track their progress. Staff needed tools to manage reservations, assign drivers and vehicles, and maintain records. Administrators needed the ability to manage training packages and user accounts.

Overall, the system was designed to make scheduling more efficient, reduce manual work for staff, and help students better prepare for their driving exams while keeping everything secure and organized.

---

## What I Did Particularly Well

One of my strengths in this project was turning business requirements into clear system models. I built UML diagrams that reflected how the system would actually function, including scheduling workflows, practice test processing, and the relationships between users, reservations, and training packages.

I also made sure security and accountability were part of the design. Role-based access and activity tracking were built into the system structure, not added as an afterthought.

---

## What I Would Revise or Improve

If I could improve one part of this project, I would spend more time refining the class diagram earlier in the process. As I continued working through the design, I realized there were cleaner ways to structure certain relationships, such as separating training packages into their own class.

In a real-world scenario, I would review early drafts with stakeholders sooner and more often to validate assumptions before finalizing the structure.

---

## Interpreting User Needs

I focused on the main concerns mentioned in the interview transcript: scheduling conflicts, organization, accessibility, and helping students prepare for exams. I translated those concerns into system features like availability checks, structured test result tracking, and role-based permissions.

Designing around user needs is essential. A system can be technically correct but still fail if it doesn’t solve the real problems the client is facing.

---

## My Approach to Designing Software

My approach starts with understanding what the stakeholders actually need and what constraints exist. I separate functional requirements (what the system must do) from nonfunctional requirements (how the system should perform). Then I model the system’s behavior and structure to make sure everything aligns.

Going forward, I plan to continue refining this approach by incorporating earlier feedback loops, scalability considerations, and risk assessment during the design phase.
